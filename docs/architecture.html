Desire Paths: architecture

A question goes left to right. Correct walks feed the learning loop (blue), and fact changes feed the heal loop (purple). Every step's number matches the talk track below.

input learned routes (no LLM) LLM calls (the cost we cut) HydraDB learning loop heal loop

Talk track (follow the numbers)

  1. Question. An agent gets a multi-hop question about a person, project, incident or service.
  2. Find the entity. SelfGraph's keyword search finds who or what the question is about. There is no vector store anywhere in the system.
  3. Seen this shape? Hide the name and you get the question's shape. If a learned route answers that shape, use it: zero LLM calls.
  4. Router. A new phrasing costs one LLM call (Gemma 4) to pick a route. The entity must match the route's start type and be named in the question.
  5. Walk. No route yet: the agent walks the graph one hop and one LLM call at a time. This is the baseline, about 5 calls per question.
  6. One query. A learned route compiles to a single Cypher query that HydraDB runs over current facts, up to 4 hops including reversed edges.
  7. Answer with provenance. The answer comes back with the exact relations and versions it used.
  8. Log the walk. Every correct walk is recorded as a typed path, such as Person → Project → Team → On-call, not names.
  9. Verify. Each candidate path is run once on HydraDB and must return exactly the answer. Coincidental shortcuts are rejected.
  10. Promote. A path that explains at least 80% of a question shape's walks, with support of 3 or more, becomes a route. The graph gets sharper with use: accuracy within one LLM call 0% → 95%, 89% fewer LLM calls.
  11. Retire. When SelfGraph supersedes a fact in HydraDB, every route whose provenance used the old version switches off.
  12. Rebuild. The route re-binds to current facts and comes back as v2, still correct. A plain cache would keep the old answer.
